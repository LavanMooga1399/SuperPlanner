# SuperPlanner M10 - eDHR, UDI/labels, validation and enterprise rollout (design + plan + acceptance)

Status: design for build, 27 November 2026. Milestone M10 of `docs/MEDDEV-GAP-PLAN.md` (size 1.4), the step from
shadow pilot to GxP use. Builds on M1-M9 as built (`docs/M1-DESIGN.md` .. `docs/M9-DESIGN.md`, cited "M7 4.2" etc.,
incl. implementation notes), `docs/DEPLOY.md` and the UX standard. Their conventions apply unchanged and are not
restated (ids, `row_version` + If-Match, error envelope, one permission per route, audit with Part 11 reasons and
old/new values, M7 signing on the action, outbox events, duty runs, expand migrations). Interpretations go to 14.

Scope: electronic device history record (eDHR, "batch record") per finished lot or WO, assembled from what the
system already records; review by exception with deviations; signed QA release lifting a `dhr` hold; server-side
PDF (PDF/A-2b) and JSON export; customer quality agreements, certificates of analysis (CoA) and batch documentation
packs (prefillable syringes for pharma customers); UDI (GS1 GTIN, AIs (01)(17)(11)(10)(21)), label templates under
ECO, print jobs with reconciliation and verification scans; GUDID and Health Canada device data export (files
only); complete validation package (IQ/OQ/PQ, trace matrix M7-M10, CSA rationale, change control, configuration
baseline, periodic review); data residency (Canada profile enforced); automated HA failover drill on the compose HA
profile plus rehearsal records; BD-scale load sign-off; multi-plant rollout playbook. Sample `meddev_m10`.

**Compliance position (unchanged).** SuperPlanner never claims compliance with 21 CFR 820/11, ISO 13485, MDSAP, GS1
or GUDID rules. M10 adds controls and evidence *designed to support* the customer's validation; the customer
decides intended use, executes and approves IQ/OQ/PQ, and owns its procedures and regulatory submissions. Every
generated document carries the footer "Generated by SuperPlanner <version>; designed to support, not a statement of
compliance."

## 0. Decisions

1. **The eDHR is assembled, not entered.** A pure function `dhr/assemble.py` builds the record from one consistent
   snapshot (primary, `REPEATABLE READ`, never the replica) of the M2 ledger, M4 floor events and serials, M5
   genealogy and ECO revisions, M7 inspection lots/results/NCRs/holds/equipment/signatures, M8 sterilisation loads,
   M10 deviations and label jobs. Nothing is copied by hand; the only human input is exception dispositions and the
   release signature. Subject = the finished **lot** (lot-controlled items; all WOs receiving into it), else the WO.
2. **Review by exception is a rules registry** (`dhr/exceptions.py`, 4.2). Each exception has a code, severity
   (`major`, `minor`, `info`), a stable fingerprint and a source reference. `major`/`minor` need a disposition;
   `info` is shown only. Dispositions carry over between versions when the fingerprint is unchanged.
3. **Release is a signed state change that lifts a hold.** WO receipt of a DHR-required item places an M7 hold with
   new source `dhr`; `POST /dhr/{id}/release` under policy `dhr.release` (reviewed: qa_engineer|qa_approver ->
   released: `final_release_role`, distinct, `password_totp`) re-assembles in the transaction (409 `DHR_STALE` if
   the content hash moved), checks releasability (4.3) and releases the hold. Other holds (inspection, sterility,
   recall) keep their own release; the lot is available only when all are released.
4. **Records are versioned, never edited.** Late source changes (floor correction, result correction, NCR, label
   events) re-assemble into a new version; a released version stays the release of record, is flagged
   `changed_after_release`, QA is notified and on-hand stock of the lot is re-held (`dhr_post_release_hold`, true).
5. **PDF without new dependencies.** An in-house writer `render/pdf.py` (~1,200 lines incl. TrueType subsetting and
   barcodes) produces deterministic PDF/A-2b: embedded subset DejaVu Sans (regular/bold, permissive licence,
   bundled), WinAnsi encoding (covers en and fr-CA), XMP metadata, sRGB OutputIntent (bundled ICC sRGB2014 profile,
   freely redistributable), Flate only, no encryption/transparency, `/ID` = content hash, `CreationDate` = record
   time, so the same content gives the same bytes. Rejected: `reportlab` (pulls Pillow + chardet - a binary imaging
   stack we do not need; PDF/A not in the open-source edition; non-deterministic output), WeasyPrint (Cairo/Pango
   system libraries), headless Chromium (300 MB image, sandbox). Conformance is checked with veraPDF (external
   binary, gate only, like k6). The browser print views of M7 stay for ad-hoc printing.
6. **Barcodes are rendered on the server only** (`udi/barcode.py`: Code 128 / GS1-128, GS1 DataMatrix ECC200 with
   Reed-Solomon), as SVG (preview, UI), PDF vectors and ZPL II (native `^BC`/`^BX`, printer renders). The UI never
   encodes DataMatrix. The M4 browser Code 128 travellers stay as they are.
7. **Labels are controlled documents.** Templates are versioned; a version becomes `approved` only by implementing
   an M5 ECO that contains it (new ECO item `doc_type label`), signed under the new policy `eco.approve_label`
   (reviewed: approver -> approved: qa_approver, distinct, author excluded). Print jobs freeze template version,
   DI and resolved data (hash). Reconciliation per job: printed (incl. reprints) = used + destroyed + retained.
8. **UDI = GS1 only in M10.** DI = GTIN-14 of an M8 packaging level (`mfg_item_packaging.gtin`); regulatory
   attributes live in `udi_device_records` (1:1 packaging row), approved by signature; a GTIN with printed labels
   cannot change (409 `UDI_GTIN_IN_USE`, a new level/GTIN is needed). HIBCC/ICCBBA, EUDAMED, GDSN are deferred.
9. **Regulatory exports are data files, never submissions.** GUDID: xlsx/CSV/JSON with GUDID data element names,
   checked by an encoded rule set (`udi/gudid_rules.py`, reference table version recorded in the file). Health
   Canada: device identifier list per licence (CSV/xlsx). HL7 SPL XML is deferred (customers use their SPL/GDSN
   provider). This interprets gap plan Gate 10 "validated against the published schema" as the encoded published
   data element rules + a hand check (14).
10. **Validation package = generated evidence, customer-approved.** `validation/package.py` builds a zip (manifest +
    sha256) from the register, trace matrix, CSA rationale, IQ checks run on the target, OQ JUnit results, PQ
    templates, baseline and diff, HA drill and load reports, release notes and procedures; approval is an optional
    in-system signature (`validation_package.approve`). The customer's QMS remains the system of record.
11. **Residency is enforced, not just documented.** Deployment declares `SP_REGION`; each organisation has an
    immutable `data_region`; requests for an org of another region are refused; archive/backup/SMTP/log/AI endpoint
    regions are declared and checked; outbound integration and the AI assistant are off for cross-region use unless
    an explicit signed exception exists.
12. **HA drill is automated on compose, rehearsal on the real rig is recorded.** A `docker compose --profile ha`
    primary + synchronous streaming replica and `scripts/ha/failover_drill.py` measure RTO and prove zero loss of
    acknowledged writes; R1-R11 rehearsal on the customer's Patroni/managed set is captured with a template.
13. **Lean delivery**: WP-S (one backend developer), WP-U (one UI developer), S0 contract freeze (days 1-2), targeted
    tests, one full suite at the end. Migration `0013_m10` (expand). No new Python or npm packages; veraPDF, k6 and
    Docker are external tools used only by the gate and scripts.

## 1. Scope and principles

Principles: G1 one source of truth - the eDHR is a view over existing append-only records plus a frozen snapshot;
G2 hard rules are never traded (releasability conditions have no override; a deviation or NCR is the documented
path); G3 every generated document is reproducible (content hash, renderer version, deterministic bytes); G4 nothing
regulated leaves the region or the system unsigned without a recorded decision.

**Out of M10 (deferred):** paper batch record scanning, electronic work instructions/MES step enforcement (BD MES
stays), label printer driver management beyond raw ZPL on TCP 9100, ISO/IEC 15415/15416 print-quality grading,
HL7 SPL / GDSN / EUDAMED submission, HIBCC/ICCBBA, aggregation (case-pallet serial hierarchy, DSCSA-style), EtO
residuals and cycle parameter capture from chamber controllers (integrate), training records and document control
(eQMS), automatic Patroni orchestration in compose, active-active multi-region.

## 4. eDHR (`dhr/`)

### 4.1 Sections (`DhrContent`, frozen at S0; each section has its own sha256)

| Section | Source | Content |
|---|---|---|
| `header` | M1/M5 | plant, item + revision, BOM/routing versions and implementing ECOs, lot, WOs, DI(s), qty planned/received/scrapped, first start, last receipt, expiry |
| `materials` | M2 ledger, M5 edges | component issues/backflush by lot and supplier lot, qty, location, posting ids, incoming inspection decision, hold state at issue time, `possible` edges marked |
| `operations` | M4 floor | per operation: events (start/report/complete/correct/reopen/skip), operators, line, equipment, times, good/scrap/rework/nc, duration vs `max_minutes`, wait vs `max_wait_minutes` |
| `equipment` | M7 | equipment linked to the lines/gauges used, calibration valid on each use date (certificate refs) |
| `inspections` | M7 | in-process and final inspection lots: plan version, sampling, results summary, decision + signatures |
| `nonconformance` | M7, M10 | NCRs with dispositions and implementation refs; applicable deviations |
| `sterilisation` | M8 | load number, chamber, cycle code, planned/actual times, aeration, release mode, release signature or failure NCR, co-sterilised lots |
| `labels` | M10 | print jobs: template code/version, DI, PI data, totals, reconciliation, verification scans |
| `serials` | M4 | count, ranges, list hash (full list only in JSON export / paged API) |
| `genealogy` | M5 | one level backward (component lots) and forward (child lots, shipments at assembly time) |
| `holds` | M7/M8 | every hold on the lot with source, placed/released, signatures |
| `review` | M10 | exceptions with dispositions, release/reject signatures (manifestation M7 4.2) |

Assembly time target P1; the signature content snapshot (M7 4.2, <= 256 KB) is `{number, version, subject,
content_sha256, section_hashes, exceptions [{code, fingerprint, disposition, ref}]}`, so a signature binds the full
record through hashes.

### 4.2 Exception rules (registry; `fingerprint` = sha256(code, ref ids, decisive data))

| Code | Severity | Condition | Allowed dispositions |
|---|---|---|---|
| `DHR_NCR` | major | NCR on the lot/WO (any state) | accepted (NCR closed), ncr |
| `DHR_DEVIATION` | info / major | approved planned deviation in scope and qty (info); unplanned or out of scope (major) | accepted, deviation |
| `DHR_CORRECTION` | minor | floor `correct`/`reopen`/`skip`, result correction (`corrects_result_id`) | accepted |
| `DHR_OVERRIDE` | minor | WO `release_override`, floor `force.reason` | accepted, deviation |
| `DHR_TIME_WINDOW` | major | operation duration > `max_minutes` or wait > `max_wait_minutes` | accepted (comment >= 20 chars), deviation, ncr |
| `DHR_YIELD` | minor | good / started < `dhr_min_yield_pct` | accepted, ncr |
| `DHR_QTY_BALANCE` | major | per operation: input != good + scrap + rework + nc (tolerance 0) | ncr, deviation |
| `DHR_LATE_ENTRY` | minor | `recorded_at - event_at` > `dhr_late_entry_hours` | accepted |
| `DHR_CAL` | major | equipment not valid on use date (should be blocked; defence in depth) | ncr |
| `DHR_MATERIAL_HOLD` | major | component lot issued while held or without an accepted incoming decision | ncr |
| `DHR_GENEALOGY_POSSIBLE` | info | `possible` edges only for a lot-controlled component | - |
| `DHR_STER` | major | load failed, missing, or released outside cycle code | ncr |
| `DHR_LABEL_RECON` | major | job not reconciled, diff != 0 explained, or a verification mismatch | accepted (after signed reconcile), ncr |
| `DHR_POST_RELEASE` | major | source changed after a released version | accepted, ncr |

### 4.3 Lifecycle, review and release

`open` (live, `GET /dhr/live`, not stored) -> `assembled` (job after the last WO receipt/close of the subject) ->
`in_review` (first disposition or `start-review`) -> `released` | `rejected`. Dispositions: `PUT
/dhr/{id}/exceptions/{xid}` (If-Match, reason in Part 11 mode); `ncr`/`deviation` dispositions reference an existing
record of the same lot/WO (422 `DHR_REF_SCOPE`). **Releasable** (else 409 `DHR_NOT_RELEASABLE`, `details.blocking[]`):
(a) every major/minor exception dispositioned; (b) referenced NCRs closed or all dispositions implemented, deviations
approved; (c) final inspection lot accepted when a final plan exists; (d) sterility hold released for sterile items;
(e) every label job of the lot `reconciled`; (f) content hash unchanged on re-assembly (409 `DHR_STALE`). Reject =
final step meaning `rejected`: hold stays, an NCR is required (`ncr_id` in the request). Release writes the frozen
PDF + JSON renditions (`doc_renditions`), releases the `dhr` hold (`release_signature_id`), emits outbox
`dhr.released`. Non-DHR plants: no hold, record and review still available (read-only evidence).

### 4.4 Deviations (`qa/deviation.py`)

Lean record (3): planned deviations approved before use (signed `deviation.approve`), unplanned ones created from an
exception or NCR; scope matching by item/lot/WO, date window and max qty (qty counted from receipts); close with
outcome; links via M7 `qa_links` (types gain `deviation`, `dhr`). System of record switch as CAPA (`deviation_sor`:
`superplanner|external`; external = reference only).

## 5. Rendering (`render/`)

`doc.py` blocks -> `pdf.py` layout: Letter/A4, margins 18 mm, header (plant, document title, number/version), footer
(page x of y, content sha256 first 12 hex, generated time with zone, compliance footer), tables with repeated
header rows and row splitting, key-value grids, signature manifestation blocks ("Released by Marie Tremblay
(mtremblay) on 2026-11-23 14:05:12 EST (UTC-05:00) - meaning: released"), vector barcodes. Bilingual layouts print
en and fr labels side by side when the plant language set has both. Glyphs outside WinAnsi -> `?` and warning
`RENDER_GLYPH_MISSING` in the rendition metadata. Layouts: `dhr` (summary 2-4 pages + full sections; serials as
ranges), `coa`, `coc`, `ster_cert`, `validation` (protocols/reports). JSON export = canonical JSON (M7 4.2 rules) of
the content plus bulk lists (serials, events) streamed; its sha256 of the content part equals `content_sha256`.

## 6. Customer agreements, CoA and batch packs (`qa/coa.py`, `qa/packs.py`)

- **Agreement** per customer (versioned, signed `customer_agreement.approve`): items, CoA characteristics (from M7
  plan characteristic codes; optional customer spec override - the M7 customer-scoped final plan is the
  inspection; the agreement decides what is reported), statement text, language, pack contents.
- **CoA** per lot x agreement (optionally a shipment line): requires the lot's DHR `released` (409
  `COA_DHR_NOT_RELEASED`); per characteristic: spec (override else plan), n, result (`value` = mean, min, max;
  `summary` = n/defects; `pass` = conforms), conformance; a result outside the customer spec -> 409
  `COA_OUT_OF_SPEC` (never printed as conforming; resolve by NCR/customer concession outside M10). Signed
  `coa.approve`; frozen PDF rendition; void with reason creates nothing new automatically.
- **CoC** (certificate of conformance) and **sterilisation certificate** are generated documents (no own table) from
  the DHR header and ster section. **Batch pack** (job `batch_pack`): zip with the agreement's documents per lot,
  `manifest.json` (file sha256, record hashes, signatures summary) and `manifest.json.sha256`; download audited.

## 7. UDI and labels (`udi/`)

### 7.1 GS1 (`gs1.py`)
GTIN-8/12/13/14 normalised to 14 digits, mod-10 check (422 `UDI_GTIN_CHECK`). Supported AIs: (01) GTIN n14, (11)
production date and (17) expiry n6 YYMMDD, (10) lot an..20, (21) serial an..20, GS1 AI encodable set 82 (422
`UDI_CHARSET`). Element string order: fixed-length AIs first (01)(11)(17), then (10), then (21); FNC1 separator
after a variable field that is not last. Outputs: data string (FNC1 = `\x1d`), HRI `(01)...(17)...(10)...`.
Expiry = lot `expires_on` (M2, from item `shelf_life_days`); missing while `pi_flags.expiry` -> 422
`UDI_EXPIRY_MISSING`. Parser accepts symbology prefixes `]d2`, `]C1`, `]Q3`, GS or `<GS>` separators and HRI form.

### 7.2 Templates (`labels.py`)
`LabelElement = {kind: text|field|barcode|box|line, x_mm, y_mm, w_mm, h_mm, rotation 0|90|180|270, font_pt, bold,
lang N, text N, field N, barcode N {symbology: gs1_datamatrix|gs1_128|code128, module_mm, ais [01,17,10,21,11]}}`.
Fields: `item.name|part_number|description`, `udi.gtin|hri|brand|catalog_no|qty_per_package`, `lot.number|expiry|
mfg_date`, `serial`, `plant.name|address`, `symbols.sterile_eo|single_use|...` (text tokens; graphic ISO 15223
symbols are customer-supplied SVG paths in the template, sanitised: path data only). Validation: elements inside the
label, barcode modules >= printer dot size (422 `LBL_MODULE_TOO_SMALL`). Draft -> added to an ECO (`in_change`,
locked) -> ECO implemented -> `approved`, previous version `obsolete`; effectivity follows the ECO (date / use-up).
Preview `GET /labels/templates/{id}/preview.svg?item_id&lot_id` uses sample or real data, watermarked "SPECIMEN".

### 7.3 Print jobs and reconciliation (`zpl.py`, `recon.py`)
Create: item + level + lot (+ WO) -> assignment (customer-specific first) -> approved template effective today
(422 `LBL_NO_APPROVED_TEMPLATE`), DI `approved` (422 `UDI_NOT_APPROVED`), lot not rejected; serialized items take
the WO's M4 serials. `issued` on creation (qty, data frozen). Output `GET /labels/jobs/{id}/output` (pdf or zpl;
first download = `printed` for target `download` once the operator confirms the count; target `printer` -> job
`label_send` writes ZPL to host:9100 from the worker, success = `printed`; private targets require
`INTEGRATION_ALLOW_PRIVATE_TARGETS`). Second output = `reprint` with reason and qty (default the whole job).
Events `used` (default proposal = WO good qty at the level / `qty_base`, confirmed), `destroyed`, `retained`
(specimens). `diff = printed + reprinted - used - destroyed - retained`; reconcile when `|diff| <=
label_recon_tolerance`, else a signed explanation (`label_job.reconcile`) records the diff and the DHR shows
`DHR_LABEL_RECON`. Job `void` only before `printed`.

### 7.4 Verification scan
`POST /labels/jobs/{id}/verify {scan, position, client_event_id}`: parse, compare every AI with the job (GTIN, lot,
expiry, production date, serial in job serials) -> `match` or `mismatch` with field diffs. Mismatch sets the job
`blocked` (no further output, reconcile refused) until a supervisor `unblock` event with reason after destroying
the wrong labels. With `label_verify_first_last`, reconcile needs a `first` and a `last` match. No print grading.

### 7.5 GUDID and Health Canada exports (`exports.py`, job `udi_export`)
GUDID: one row per approved DI (+ package DIs with `contains_gtin`), columns = GUDID data element names, values
mapped from attrs (14.1); `gudid_rules.py` checks required elements, lengths, enumerations, GTIN check, package
hierarchy consistency, PI flags vs label templates (a DI whose template omits (17) while `pi_flags.expiry` ->
error). Health Canada: rows per licence: licence no, class, device name, catalog/model no, DI, issuing agency,
qty. Output xlsx (openpyxl, existing), CSV, JSON; result lists errors/warnings per DI; files carry `rule_version`.

### 9.1 Data residency (`orgs/residency.py`)
Env: `SP_REGION` (e.g. `ca`), `SP_REGION_ENDPOINTS` JSON `{archive, backup, smtp, logs, ai}` -> region tag each

### 9.2 HA failover drill
Compose profile `ha`: `db` gets `wal_level=replica`, `synchronous_standby_names='FIRST 1 (replica1)'`, a
replication role; `db-replica` (`scripts/ha/replica-entrypoint.sh`: `pg_basebackup -R`, `application_name=replica1`).
API/worker `DATABASE_URL` uses libpq multi-host `host=db:5432&host=db-replica:5432&target_session_attrs=read-write`
(SQLAlchemy psycopg multi-host), so no HAProxy is needed. `scripts/ha/failover_drill.py` (stdlib + httpx): check
`pg_stat_replication.sync_state = sync` -> run writes (floor events and postings with idempotency keys, 20/s) and
reads, logging every acknowledged id -> `docker compose kill db` -> `SELECT pg_promote()` on the replica -> measure
until `/health/ready` 200 and the first acknowledged write (RTO) -> verify every acknowledged write exists exactly
once (RPO 0), only 503 `DB_UNAVAILABLE` during the gap (no 500), `audit-verify` ok, sample signature `verify` ok ->
JSON + markdown evidence with sha256 -> optional `--rebuild` re-seeds the old primary as replica (R3 analogue).
Wrapper `tests/ha/test_failover_compose.py` (marker `ha_compose`, skipped unless `SP_HA_COMPOSE=1`). Real-rig
rehearsal of R1-R11 uses `templates/ha-rehearsal.md` (steps, expected, observed, timings, signer), uploaded as
evidence.

### 9.3 Load sign-off and org audit

&actor&page` (org_admin, new org role `org_auditor`) merges plant audit chains read-only; `manage.py audit-verify

### 9.4 Multi-plant rollout (`docs/ROLLOUT.md`)
